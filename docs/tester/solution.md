# Solution Review

## Main Goals

The main goals of this stage are:
- Independently solve the problem and write another correct solution.
- Check that all solutions intended to be correct are accepted on every current test.
- Investigate and report any disagreement or suspicious behavior.

::: info Polygon checklist for this stage
- Upload an independently written correct solution in Polygon.
- Run an invocation with the tester's solution, the main correct solution, and all current tests.
- Investigate every unexpected verdict or disagreement.
:::

## Writing an Independent Solution

Solve the problem independently before relying on the setter's solution.

The tester's solution may use the intended algorithm or a different correct algorithm. The important point is that it should be developed independently, so that it provides additional evidence that the statement and main correct solution are correct.

::: warning Do not review the main correct solution as source code
In our workflow, solutions are treated as black boxes. Do not validate the setter's solution by reading its implementation. Instead, write an independent solution and compare their behavior through tests.
:::

::: danger Justify the solution before implementing it
Before coding, rigorously justify why your algorithm is correct and why its time and memory complexity fit the constraints. An independent implementation is useful only when its underlying algorithm is trustworthy.
:::

Upload the solution in the `Solutions` tab in Polygon, following the solution filename rules.

::: info For now, write only a correct solution
Do not intentionally write WA or TLE solutions yet. They will be covered in the following testing-review stage.
:::

## Comparing Solutions

Run an invocation containing all current solutions and tests. Every solution intended to be correct should be accepted on every test.

For problems with a unique output, independently written correct solutions should produce the same output. For problems with multiple valid outputs, their outputs may differ, but the checker should accept all of them.

If a solution intended to be correct fails any test, investigate immediately. Possible causes include:

- one of the solutions is incorrect;
- the test is invalid;
- the statement is ambiguous or missing a condition;
- the checker accepts or rejects an output incorrectly;
- the jury answer generated by the main correct solution is incorrect.

If the failing test is too large to investigate directly, use stress testing or exhaustive small tests to find a smaller input where the solutions behave differently. See [Polygon Manual: Stress](../polygon/) for details.

You may discover that your own solution is incorrect. In that case, fix it and repeat the comparison. We recommend keeping the original incorrect code in Polygon under a different name, such as `username_wa1.cpp`, because it may be useful as a wrong solution during the testing stage.

If another solution is incorrect, or the problem lies in the statement, checker, test data, or another package component, report the issue to the relevant code writer or setter.

## Reporting Issues

When reporting a disagreement, include:

- the input where it occurs;
- the verdict or output of each solution;
- which component you believe is incorrect;
- why it is incorrect;
- how it could be fixed, if known.

A small counterexample is usually much easier to investigate than a large failing test.

## Before Moving On

::: tip Ready to move on when
- An independently written full solution is uploaded in Polygon.
- The tester has rigorously justified the correctness and complexity of their solution.
- All solutions intended to be correct are accepted on all current tests.
- Every disagreement has been investigated and resolved.
- **The changes are committed on Polygon.**
:::
